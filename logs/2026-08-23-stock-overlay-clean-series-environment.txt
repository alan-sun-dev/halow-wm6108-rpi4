================================================================
WHY THIS RUN EXISTS
================================================================
Every previous passing run on this board -- phy31 (the first "it works"), phy33
(the clean-series verification behind commit abe3632) and phy35 -- was made with
`overlays/mm610x-spi-sensecap-experiment-all.dts` installed over the stock
filename `mm610x-spi-sensecap.dtbo`. That overlay sets

  reset-gpios = <&gpio 17 0>

which is OpenMANET's setting, under which RESET_N never actually fires. It also
adds a single `cs-gpios` entry and changes the pin pulls. `config.txt` says only
`dtoverlay=mm610x-spi-sensecap`, so the filename gives no hint that a different
overlay is loaded; the dtbo mtime is the only local tell.

That meant the combination actually being shipped -- clean series + the repo's
stock overlay, where RESET_N does fire -- had never been measured. Both halves
had been measured, never together. This run closes that gap.

chip with CS asserted before the fixed module was inserted, and the fixed module
still recovered. The "once addressed with CS asserted it does not recover" rule
in NOTES.md applies to a training burst with no preceding reset -- probe resets
the chip first, then bursts, which is the order 0002 requires.

OPERATION
================================================================
Measured with the SPI core's own counters, which depend on nothing this repo
wrote (/sys/bus/spi/devices/spi0.0/statistics/):

  ip link set wlan1 up    +11 messages
  iw dev wlan1 scan       +19 messages
  iw dev wlan1 scan       +23 messages
  idle, 35 s              +250 messages   (30 s watchdog)
  errors 0   timedout 0   throughout

wlan1 sits at operstate down / NO-CARRIER with the interface UP, and the scans
return nothing. That is the absence of any HaLow network in range, not a fault:
the scans reach the chip, which is what the counter deltas show.

Association and data transfer remain untested, for want of a second HaLow
device. Nothing about the driver is in doubt.


================================================================
WHAT THIS CHANGES
================================================================
Nothing in patches/upstream/ needed to change. The series is unmodified, and it
is now measured in the configuration the repo actually tells people to build:
stock overlay, RESET_N firing, two chip selects, no module parameters beyond
country= and bcf=.

What it removes is a hole in the evidence. Until this run, the passing result and
the stock device tree had never been observed at the same time, and the overlay
that was actually installed disabled RESET_N -- the very thing 0002 exists to
survive. Had the fixes depended on that overlay, the repo's own instructions
would not have reproduced its own result, and nothing on hand would have shown it.

Method note, consistent with the rest of this investigation: the first attempt at
reading the device tree used `xxd`, which is not installed on this image, and the
error was being swallowed by a `2>/dev/null` on the same line. Every reading above
was re-taken with `od` and a positive control alongside it.
