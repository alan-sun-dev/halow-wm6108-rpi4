  so the instrumentation did not change behaviour.

  NEW FACT — spi_setup() puts SPI_CS_HIGH back:
      init: mode=0x4 cs_high_default=1 train=18 flip=1
      init: CS deasserted for training, mode=0x4     <-- expected 0x0
      init: CS polarity restored, mode=0x4
  mode is 0x4 (SPI_CS_HIGH) at all three points, including immediately after
  `spi->mode &= ~SPI_CS_HIGH; spi_setup(spi);`. The SPI core forces SPI_CS_HIGH
  back on for a cs-gpios device. So morse_spi_initsequence()'s whole purpose --
  clocking the training burst with CS *deasserted* -- never happens on any
  cs-gpios kernel. See RUN 2: this is a real driver defect but it is NOT the
  cause of the skew.

  NEW FACT — the default ack search window is 11 bytes, not 71:
      find_data_ack failed: no non-0xff byte in the 11 bytes clocked after CRC
  The "71 bytes" in earlier notes was the length of a hex dump, not the window.

RUN 5 — the skew with the driver entirely out of the picture
================================================================
  log: 2026-08-22-bookworm-6.6.51-retest-spidev.txt

  No reboot and no config.txt change were needed. tools/mmcspi.py's docstring
  gives the trick: bind spidev to the existing spi0.0 with driver_override, so
  the overlay stays in place and GPIO18 slot power and the GPIO17 pull-up are
  preserved.

      sudo rmmod morse
      echo spidev | sudo tee /sys/bus/spi/devices/spi0.0/driver_override
      echo spi0.0 | sudo tee /sys/bus/spi/drivers/spidev/bind

  Note: mmcspi.py's reset_module() calls gpioset with libgpiod **v2** syntax
  (-c/--hold-period/-t0). This image ships libgpiod v1.6.3, where that fails
  silently -- sh() captures output and discards it -- so the reset pulse never
  happens and only the `pinctrl set 17 ip pu` line takes effect. Pulse RESET_N
  by hand first:
      sudo pinctrl set 17 op dl; sleep 0.05; sudo pinctrl set 17 ip pu

  RESULT — the skew is present with no driver loaded, on this kernel:
      CMD0  correct CRC   R1=0x01 @bit10   raw=ff c0 7f ff ff ff
      CMD0  bad CRC       R1=0x09 @bit10   raw=ff c2 7f ff ff ff
      CMD13               R1=0x05 @bit10   raw=ff c1 7f ff ff ff
      CMD63               R1=0x01 @bit10   raw=ff c0 7f ff ff ff
      clocks, no command  no response (all 0xff)
  Same 2-bit offset previously measured on Trixie 6.18.34. The chip still
  validates our CRC7 and flags illegal commands, so its receive path is fine.

  NEW — the offset does not depend on where the command sits in the transfer.
  Sweeping the number of 0xff bytes clocked before CMD0 inside the same CS
  assertion:
      n = 0, 1, 2, 3, 4, 8, 16, 32  ->  R1=0x01 @bit10 in every case
  So this is NOT the controller mis-sampling the first bits of a transfer. The
  chip's response is genuinely 2 bit-times late relative to the command's byte
  grid, wherever in the transfer that command appears.

  NEW — modes 0, 2 and 3 are byte-identical; only mode 1 differs:
      mode 0 / 2 / 3, 400 kHz and 1 MHz:  ff c0 7f ...  zero-run at bit 10
      mode 1:                             unstable, zero-runs wander
  Modes 0 and 3 sampling alike is expected (both sample on rising edges), but
  modes 1 and 2 both sample on falling edges and should therefore behave alike
  -- and they do not. Recorded as an observation; no mechanism claimed.

  State restored afterwards: driver_override cleared, spidev unbound, morse
  reloaded and bound to spi0.0.

WHERE THIS LEAVES IT (after run 5)
================================================================
Same board, same wiring. Eliminated: kernel tree (source byte-identical),
ack-window padding, the driver's init sequence, the pin mux, the clock rate,
and now the driver itself -- the skew is identical through /dev/spidev0.0 with
no driver loaded, and does not depend on where the command sits in the transfer.

What is left is a genuine disagreement between the chip and the host about where
byte boundaries are, established somewhere at or before the first response, on a
board where the OpenMANET image needs no compensation at all.

RUN 6 — is the skew set by the pull on MISO/MOSI/SCLK?   ELIMINATED
================================================================
  Found by decoding OpenMANET's own overlay off a freshly written card (see
  2026-08-22-openmanet-1.8.0-overlay-mm610x-spi.txt): it sets

      spi0_pins { brcm,pins = 9 10 11; brcm,function = ALT0; brcm,pull = 2 2 2 }

  i.e. pull-UP on all three SPI lines. The overlay in this repo does not touch
  those pulls and inherits the BCM2711 default, which is pull-DOWN. Confirmed on
  the running board:

      9: a0  pd | hi // GPIO9 = SPI0_MISO
     10: a0  pd | lo // GPIO10 = SPI0_MOSI
     11: a0  pd | hi // GPIO11 = SPI0_SCLK

  The idea: an MMC-SPI slave tri-states MISO before it answers, so the level
  during those bit times is set by the pull rather than by the chip.

  Tested with spidev bound via driver_override, flipping the pulls at runtime
  with `pinctrl set 9|10|11 pu` -- no reboot, no overlay change:

    A. pull-down (as shipped here)
       CMD0  correct CRC   R1=0x01 @bit10   raw=ff c0 7f ff ff ff
       CMD0  bad CRC       R1=0x09 @bit10   raw=ff c2 7f ff ff ff
       CMD13               R1=0x05 @bit10   raw=ff c1 7f ff ff ff
       CMD63 arg=0         R1=0x01 @bit10   raw=ff c0 7f ff ff ff

    B. pull-up (OpenMANET's setting)
       CMD0  correct CRC   R1=0x01 @bit10   raw=ff c0 7f ff ff ff
       CMD0  bad CRC       R1=0x09 @bit10   raw=ff c2 7f ff ff ff
       CMD13               R1=0x05 @bit10   raw=ff c1 7f ff ff ff
       CMD63 arg=0         R1=0x01 @bit10   raw=ff c0 7f ff ff ff

  Byte-identical across all seven commands in both directions. The pull is not
  the variable.

  Worth noting the reasoning never closed even before the test: the captured
  bits ahead of R1 are `11`, i.e. high, which a pull-down would not produce. The
  test confirms that gap was real rather than a detail of the explanation.

  State restored: pulls back to pd, spidev unbound, morse reloaded.

BOARD IDENTITY — recorded late, and why it matters
================================================================
These environment files recorded only `Host: Sensecap`, and there turn out to be
two SenseCAP M1 units, both with that hostname. That made it impossible to tell
from the archive which board a given run used, and it briefly looked as though
the whole working-vs-failing comparison had been made across two different
boards.

It had not. The archived boot dmesg logs carry the board's MAC in the kernel
command line, and they settle it:

  2026-08-22-bookworm-6.6.51-boot-dmesg.log    smsc95xx.macaddr=E4:5F:01:52:57:E7
  2026-08-22-bookworm-6.12.93-boot-dmesg.log   smsc95xx.macaddr=E4:5F:01:52:57:E7
  2026-08-22-openmanet-1.8.0-full-dmesg.log    smsc95xx.macaddr=E4:5F:01:52:57:E7
  2026-08-22-openmanet-1.8.0-ab-full-dmesg.log smsc95xx.macaddr=E4:5F:01:52:57:E7

So board E4:5F:01:52:57:E7 has been observed both failing under Raspberry Pi OS
(6.6.51 and 6.12.93) and working under OpenMANET. The "same board" claim in this
repo and in the issue #9 comments holds, and is backed by the logs rather than by
memory.

The retest runs above (RUN 0-6) have no such line, because dmesg was cleared
before each insmod, so they do not identify their own board. They were on the
same card in the same machine as the 6.6.51 boot log, so they were on 57:E7 too.

A trap worth writing down: the retest-*.log files live on the SD card, not on the
board. Finding them on a machine proves only that the card has been in it since,
not that the run happened there. That confusion is what produced the false alarm.

From now on every environment file records the board MAC and serial. Two units of
the same product with the same hostname is exactly the situation where "which
machine was that?" stops being answerable after the fact.

Second unit, for the record:
  E4:5F:01:52:55:04, serial 100000004851d437, Raspberry Pi 4 Model B Rev 1.4
It runs Raspberry Pi OS 6.6.51 from the same card and shows a byte-identical
failure -- `c0 3f` / `c0 7f`, CMD63 ret:-71. A second board with a second module
reproducing the skew is corroboration that it is not one unit's defect.

RUN 7 — the four device-tree differences from the A/B   ALL ELIMINATED
================================================================
  Run on board E4:5F:01:52:55:04 (192.168.200.182), Raspberry Pi OS 6.6.51,
  driver mm6108-2.0.1 with patches/morse-driver-2.0.1-rpi-spi.patch @ 000fbbe.

  The A/B (logs/2026-08-22-openmanet-1.8.0-ab-environment.txt) found four
  differences between the working and failing device trees. Two overlay changes
  closed all of them.

  (a) One chip select instead of two.
      Added to the &spi0 fragment:   cs-gpios = <&gpio 8 1>;
      Added to the &gpio fragment:   spi0_cs_pins { brcm,pins = <8>; ... }
      -- the second override is needed because the base rpi DT declares
      spi0_cs_pins as <8 7>, so GPIO7 stays claimed otherwise.

      Verified in effect after reboot:
        /proc/device-tree/soc/spi@7e204000/cs-gpios is 12 bytes (was 24)
        pin 7 (gpio7): (MUX UNCLAIMED) (GPIO UNCLAIMED)      <- was gpio_out
        pin 8 (gpio8): fe204000.spi ... function gpio_out

      Result: morse rx c0 3f / c0 7f, CMD63 ret:-71. Unchanged. ELIMINATED.

  (b) reset-gpios flag 0 instead of 1, matching OpenMANET.
      reset-gpios = <&gpio 17 0>;

      Verified in effect: the property reads 00000007 00000011 00000000.

      Result: unchanged. ELIMINATED.

      This one was more interesting than it looks and is worth recording. The
      flag is GPIO_ACTIVE_LOW, and morse_hw_reset() asserts with
      gpiod_set_value(reset, 1). With flag 1 that drives the pin low and RESET_N
      really fires; with flag 0 it drives high, so on OpenMANET the driver's
      reset pulse plausibly never happens at all. Given that fixing
      reset_module() in tools/mmcspi.py -- making the reset actually occur --
      changed CMD0's tail from `ff c0 7f` to `1f c0 7f`, "the reset pulse itself
      puts the chip into the skewed state" was a real hypothesis. It is now
      dead: with the flag matching OpenMANET the skew is identical.

  The failing board's spi0 node now matches the working one on every difference
  the A/B found -- cs-gpios, GPIO7, reset-gpios -- and spi-max-frequency was
  independently swept in RUN 4. The device-tree avenue is exhausted.

  Both overlay changes are still installed on 55:04; the stock dtbo is backed up
  at /boot/firmware/overlays/mm610x-spi-sensecap.dtbo.orig.

  What has never been compared: the base bcm2711-rpi-4-b.dtb (firmware partition
  on Raspberry Pi OS vs built by OpenWrt), the VideoCore firmware (start4.elf,
  fixup4.dat), and the kernel config. The VideoCore firmware is the interesting
  one -- it configures the SoC clock tree before the kernel starts, the symptom
  is a bit-level timing offset, and it is the one thing guaranteed to differ
  between the two images that has never been looked at.
