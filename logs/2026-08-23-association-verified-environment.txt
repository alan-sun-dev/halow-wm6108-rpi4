================================================================
A CORRECTION FIRST
================================================================
README, NOTES, logs/2026-08-23-WORKING-environment.txt and the description of
morse_driver#16 all say the scans return nothing "because there is no HaLow
network in range". That is wrong. There was a HaLow AP broadcasting a few
metres away, and had been for hours, throughout every scan quoted.

The reason it was invisible: the AP was on `country=US` and the station on
`country=SG`. Under the dot11ah mapping the same mapped channel number resolves
to a different real S1G frequency depending on country, so the station scanned
a channel plan the AP was not on.

Measured before and after, nothing else changed:

  AP country=US, station country=SG
    iw dev wlan1 scan freq 5785   -> empty
    iw dev wlan1 scan             -> 0 BSSes

  AP country=SG, station country=SG
    iw dev wlan1 scan freq 5785   -> BSS 3c:1a:cc:70:3f:ca, SSID BCM2711-57e7,
                                     RSN authentication suites: SAE

The claim should have been "no network on the channel plan being scanned". It
was never checked against the AP that was sitting on the same bench.


================================================================
BRINGING THE TWO ONTO THE SAME REGULATORY DOMAIN
================================================================
`country=SG` is what TESTING.md specifies for this location: 920-925 MHz, 4 MHz,
22 dBm, the only built-in region that fits the Taiwan NCC allocation. The AP was
found on `country=US`, which is what OpenMANET ships.

On the AP (config backed up to /etc/config/wireless.bak-20260823):

  uci set wireless.radio1.country='SG'
  uci commit wireless
  wifi reload

hostapd's own resolution of that, from logread:

  morse_set_interface: s1g_chan_center=42, ht_center_chan=159, ht_chan=157
  S1G operating channel 42 (BW: 2, freq: 923000, local class: 20)
  S1G primary channel 41 (BW: 1, 1MHz primary chan index: 0, global class: 68)
  wlh0: interface state COUNTRY_UPDATE->ENABLED
  wlh0: AP-ENABLED

Transmit power dropped from 27.00 dBm to 22.00 dBm when the country changed,
which is the SG limit taking effect and matches what TESTING.md documents.

One error is logged during the switch and is not fatal:
`Channel 41 not found for s1g/global operating class 17/66`. The AP enables
anyway and serves clients.

Downlink is steady at 1.3-1.5 Mbit/s. Uplink completes every time with correct
data but varies by a factor of four. Both are well below the 7.52 Mbit/s the AP
reports as expected throughput, which is a driver estimate rather than a
measurement. At 2 MHz bandwidth these figures are not obviously wrong, but no
attempt has been made here to find the ceiling or to explain the uplink spread.

The truncated first attempt is the only failed transfer, and it happened on the
very first sustained transfer after association. It did not reproduce in four
subsequent transfers. Recorded, not explained.

A methodological note, because it nearly went into the record wrong: the first
uplink measurement was taken by piping the file the truncated download had left
behind, and dividing by the intended 4194304 rather than the 155648 bytes that
actually moved. Both numbers reported from that run were wrong. Every figure
above is the byte count confirmed at the receiving end, divided by the measured
elapsed time.

Driver errors in dmesg for the entire session: one line.

-110 is ETIMEDOUT. It appears once, at the first association, and never during

Three authenticate/associate cycles are in the log and no deauthentication,
disassociation or beacon-loss event at all, so the link re-associated twice
without any logged reason. Unexplained.

Both sides report `signal: 0 dBm` and `signal avg: 0 dBm`. The driver does not
report RSSI, so there is no link-margin figure in any of this and no way to tell
from these numbers how much headroom the link has. The two boards were on the
same bench, a few metres apart.

CORRECTED 2026-08-23 later: "the driver does not report RSSI" is wrong. It does.
A third node -- a Heltec HT-H7608, same MM6108, joining this same AP from a few
metres away -- reads -71 to -75 dBm and varies, while our station on the same
bench reads 0 in the same minute, in the AP's own hostapd log and in
`iw station dump`. The measurement path works; a 0 is what this driver reports
when the signal is off the top of the scale, which at 22 dBm over the ~0.3 m
between these two boards is where it would be (free-space loss at 923 MHz over
that distance is about 21 dB, so roughly +1 dBm arrives). The saturation
explanation is not proven -- the attenuation test that would prove it has not
been run. What is certain is that the earlier claim was drawn from two boards
that were never far enough apart to produce a measurable number. See NOTES.md,
"Reading the link: RSSI, the numbers `iw` prints, and one way to brick the
radio".
