Read-only on the station (node 2, the soak node). No GPIO was written, no
overlay loaded, no reboot. Every command below reads.

Motivation: HARDWARE.md carries a TBD row for the HAT button / fan / LED
pins, and the 2026-08-27 survey established only that all four HAT devices
are UNDECLARED in software. This capture asks a different question -- not
what software declares, but what the pins are actually doing.

===== what debugfs shows, and why it is not the same question =====
 gpio-517 (GPIO5               |mm610x_spi_irq_gpio ) in  hi IRQ 
 gpio-519 (GPIO7               |spi0 CS1            ) out hi ACTIVE LOW
 gpio-520 (GPIO8               |spi0 CS0            ) out hi ACTIVE LOW
 gpio-529 (GPIO17              )
 gpio-530 (GPIO18              |halow-slot-power    ) out hi 
 gpio-535 (GPIO23              |morse-wakeup-ctrl   ) out hi 
 gpio-536 (GPIO24              |morse-async-wakeup-c) in  lo IRQ 
 gpio-539 (GPIO27              )

GPIO 17 carries NO named consumer in debugfs and reads as a plain
`INPUT pull=UP level=1` -- yet the live device tree says it is RESET_N.
Both are true: `morse_driver` 2.0.1 contains no `gpiod_` call at all and drives
the pin through the legacy integer API (`gpio_direction_output` / `_input`),
which registers no consumer, and `morse_hw_reset()` leaves the line floating as
an input on release, the pull-up in the overlay holding it high.

**So a pin survey built on debugfs cannot see a legacy-API user, and will report
a load-bearing pin as free.** That is what happened on 2026-08-27.

===== the one unexplained line: GPIO 27 =====
Three lines read high against a pull-DOWN, i.e. something external is driving
them:

  GPIO  5   INPUT  pull=DOWN  level=1   -- known: the Morse IRQ
  GPIO  9   alt0   pull=DOWN  level=1   -- known: SPI0_MISO
  GPIO 27   INPUT  pull=DOWN  level=1   -- NOTHING ACCOUNTS FOR THIS

An input held high by an external pull-up, idle, is exactly how a button is
normally wired: high at rest, pulled low when pressed. GPIO 27 is therefore the
first electrical evidence of a specific HAT device on a specific pin, and it
narrows a 20-pin candidate set to one lead.

NOT ESTABLISHED: that it is the button. The zero-risk confirmation is to sample
GPIO 27 while somebody presses the panel button -- a pure read, safe even on the
soak node. It has not been done, because it needs a person at the box.

===== the fan: not observable from software at all =====
The ONLY lines driven as outputs on the station are:

  GPIO  7  OUTPUT hi   spi0 CS1
  GPIO  8  OUTPUT hi   spi0 CS0
  GPIO 18  OUTPUT hi   halow-slot-power
  GPIO 23  OUTPUT hi   morse-wakeup-ctrl

Every other line is an input. Nothing drives a fan, and no line is configured as
a tachometer input. The AP -- the other SenseCAP M1, same chassis, a different
image (OpenMANET) -- declares no fan, button or HAT LED either; its only extra
named pins are `gps-wm1302` on GPIO 12 and GPIO 25, a WM1302 LoRa leftover.

So if the fan turns, it turns because the HAT wires it to a rail, not because
the Pi asks. **Its state cannot be read from software on either M1.**

That is the real obstacle, and it is not a risk one: THE FAN IS ITS OWN READOUT.
Driving a candidate pin proves nothing remotely, because nothing here can tell
whether the fan started. Pin-hunting for it needs a person at the box.

===== thermal, for what it is worth =====
  station (M1, RPi OS)   temp=41.8'C
  AP (M1, OpenMANET)     temp=51.1'C
  dkmstest (RAK chassis) temp=42.3'C

Both Pis report `throttled=0x0` after 22 days: neither has ever been throttled.
Ten degrees between two identical chassis is suggestive and NOT conclusive --
the AP runs hostapd, NAT and routing on a different OS in a different room, and
ambient is uncontrolled. The decisive remote test is a thermal step response:
load the CPU, watch the plateau and the cooling tail, since a sealed box with no
airflow plateaus far higher and cools slowly. NOT RUN -- it means loading either
the soak node or the production AP.

===== candidate set, if the hunt is ever run =====
Excluded: 5, 7, 8, 17, 18, 23, 24 (DT-claimed HaLow -- 17 is RESET_N);
          9, 10, 11 (SPI0); 0, 1 (HAT ID EEPROM);
          27 (externally driven -- driving it would contend);
          14, 15 (UART, if a serial console is wanted).
Remaining: 2, 3, 4, 6, 12, 13, 16, 19, 20, 21, 22, 25, 26.
All thirteen currently read as inputs at the level of their own pull, so none is
externally driven and contention risk is low.

`dtoverlay -h gpio-fan` defaults to `gpiopin=12`, and the AP's device tree names
GPIO 12 `gps-wm1302`. That is a coincidence of defaults and a LoRa leftover, not
evidence -- but 12 is worth trying first.

Permanent form once the pin is known:
  dtoverlay=gpio-fan,gpiopin=N,temp=55000     (registers a cooling device)
  dtoverlay=gpio-key,...                      (button; a long-press restoring a
                                               known-good HaLow config is the
                                               unattended-recovery trigger this
                                               project still lacks)
Test form, reversible:
  sudo pinctrl set N op dh / op dl / ip
`pinctrl`, `raspi-gpio` and `dtoverlay` are all present on the station.

===== instrument notes from this capture =====
1. `find /proc/device-tree -name reset-gpios` returned NOTHING with rc=0.
   /proc/device-tree is a SYMLINK to /sys/firmware/devicetree/base and find does
   not follow symlinks without -L. The property was there all along. A silent
   empty result from find is not a negative.
2. `xxd` does not exist on Raspberry Pi OS Lite; `od -An -tx4` is the portable
   form, remembering that it byte-swaps big-endian DT cells on this host.
3. The find in note 1 was first run with `2>/dev/null` attached -- the same
   redirect this project has now been bitten by three times.
